# Подключение к реальным системам и пилот

Режим CONNECTED предназначен для ограниченного пилота после проверки контрактов на конкретных установленных версиях Splunk, TheHive и MISP. Начинайте с чтения и ручного разбора (`observe`). Не используйте учётные данные или том PostgreSQL от DEMO для CONNECTED: при первом запуске создаются пользователи и политика заказчика, а повторное заполнение существующей БД не выполняется.

## Подготовка

1. Разверните отдельную копию проекта со своим `.env` и томами БД/Redis. Для всех команд ниже в PowerShell задайте имя Compose-проекта, отличное от DEMO, например `$env:COMPOSE_PROJECT_NAME = 'soc-pilot-01'`; при повторном открытии терминала задайте его снова. Скопируйте `.env.example` в `.env`, задайте `MODE=CONNECTED`, сильные `POSTGRES_PASSWORD`, `JWT_SECRET`, `WEBHOOK_SECRET` и `CONNECTED_ADMIN_PASSWORD`. При необходимости задайте `CONNECTED_ANALYST_PASSWORD`. Секреты JWT и webhook должны быть разными, длиной от 32 символов и без демонстрационных префиксов. Пароли CONNECTED должны иметь 12–256 символов, без пробелов по краям и префиксов `demo-`, `change-`, `replace-`; иначе приложение не стартует. Не храните реальные значения в Git. Приложение отвергает БД, в которой уже есть заказчик другого режима. Если DEMO запущен на том же компьютере, сначала освободите опубликованный порт `5173` либо используйте другой хост.
2. Ограничьте доступ к адресу сервиса, настройте TLS на внешнем reverse proxy и журналирование без секретов. В текущей конфигурации Compose наружу опубликован только порт веб-интерфейса `5173`; API доступен через его `/api/` proxy. Встроенный nginx не пишет access log для `/api/`, поскольку путь webhook содержит секрет; проверьте журналы всех внешних proxy и балансировщиков. Проверьте фактический сетевой маршрут и правила доступа до приёма событий.
3. Выдайте отдельные API credentials с минимальными правами и задайте `SPLUNK_BASE_URL`, `SPLUNK_TOKEN`, `THEHIVE_BASE_URL`, `THEHIVE_API_KEY`, `MISP_BASE_URL`, `MISP_API_KEY`. Используйте HTTPS с доверенным сертификатом. Клиенты выполняют проверку TLS и ограничивают время запросов. Для проверенного адаптера TheHive 5.7 явно задайте `THEHIVE_API_VERSION=5.7`; пустое значение или иная версия запрещает запись. Сверьте фактическую версию по `/api/v1/status` вашей установки до пилота.
4. Настройте фиксированный `SPLUNK_SEARCH_TEMPLATE` со строго разрешённым index и окном `{earliest}`/`{latest}`. При необходимости передайте JSON с отдельными шаблонами по ключам правил и `_poll` через `SPLUNK_RULE_TEMPLATES_JSON`. Адаптер создаёт ограниченное поисковое задание Splunk, проверяет его завершение и постранично читает результаты; лимиты задают `SPLUNK_SEARCH_TIMEOUT_SECONDS`, `SPLUNK_MAX_CONCURRENT_SEARCHES`, `SPLUNK_PAGE_SIZE`, `SPLUNK_MAX_WINDOW_SECONDS`. Проверьте шаблоны на своей версии Splunk, включая поля связанных событий, полноту результатов, окно при рестарте и права токена. `SPLUNK_POLL_SECONDS` и `SPLUNK_OVERLAP_SECONDS` задают частоту и перекрытие опроса; Compose передаёт их в `backend`, `worker` и `beat`.
5. До запуска CONNECTED примените все миграции Alembic до `head`: `docker compose build backend`, затем `docker compose run --rm backend alembic upgrade head`. После этого запустите `docker compose up --build -d` и проверьте `docker compose ps`, `docker compose exec backend alembic current`, вход, `/api/health/ready`, страницу интеграций, поступление алерта, расследование и аудит. Состояние доступности API и фактическая свежесть событий проверяются отдельно.

Для прямой ссылки из раздела «Кейсы» на интерфейс TheHive можно дополнительно задать `THEHIVE_CASE_URL_TEMPLATE` после проверки фактического маршрута UI на вашей установке. Шаблон должен содержать ровно один `{case_id}` в пути и иметь тот же HTTPS origin, что и `THEHIVE_BASE_URL`; HTTP допустим только для loopback. Приложение кодирует внешний ID как сегмент URL и не создаёт ссылку для неподтверждённой синхронизации, режима DEMO или неподходящего шаблона. Пустой шаблон оставляет ссылку скрытой. Пример конкретного пути здесь не приводится, потому что он зависит от установки TheHive.

## Локальная Ollama

Модель необязательна. Когда `OLLAMA_BASE_URL` и `OLLAMA_MODEL` пусты, решения формирует помеченный детерминированный анализатор. Чтобы включить Ollama в локальной сети Compose, сначала запустите только сервис модели и **отдельным контролируемым шагом** загрузите заранее выбранную модель:

```powershell
docker compose --profile llm up -d ollama
$approvedModel = 'имя-и-тег-утверждённой-модели'
docker compose --profile llm exec ollama ollama pull $approvedModel
```

После загрузки задайте в `.env` `OLLAMA_BASE_URL=http://ollama:11434` и `OLLAMA_MODEL` равным точному имени и тегу загруженной модели, затем запустите `docker compose --profile llm up --build -d`. Автоматической загрузки модели при старте нет. Порт Ollama не опубликован на хосте. Для полностью офлайн-развёртывания заранее перенесите проверенный локальный model store в том `ollama_data` и не разрешайте сервису выход в Интернет. Переменная `OLLAMA_NO_CLOUD=1` в Compose запрещает облачные функции сервера; приложение дополнительно проверяет `/api/tags` перед передачей событий и отклоняет модели с признаками удалённого исполнения. Сам по себе локальный адрес не доказывает, что модель локальна.

`OLLAMA_TIMEOUT_SECONDS`, `OLLAMA_MAX_INPUT_CHARS`, `OLLAMA_MAX_OUTPUT_BYTES`, `OLLAMA_NUM_CTX` и `OLLAMA_MAX_CONCURRENT` ограничивают запрос. Последний предел действует в каждом процессе worker; суммарный лимит нескольких процессов дополнительно определяется их количеством и настройками Ollama. Приложение передаёт только ограниченный набор доказательств с базовым маскированием распространённых секретов; сверьте реальные схемы логов и сетевую изоляцию до передачи чувствительных данных. Структурированный ответ проверяется по схеме, существующим ID доказательств и связанных событий; предложение модели не даёт права на внешнее действие без серверных правил. Сохраняются предложение класса и уверенности, доказательства «за/против», связанные события, MITRE, имя и digest модели, версия и SHA-256 промпта (`0008_llm_provenance`). Уверенность модели не является калиброванной вероятностью. Если настроенная Ollama недоступна, не отвечает или её результат непроверяем, итог получает `INCONCLUSIVE` / `needs_review` и только действие `review`; детерминированный вывод остаётся материалом для аналитика, автоматические действия не выполняются. Ollama не получает инструменты и не может выполнять действия напрямую.

Текущая реализация предполагает один настроенный набор API endpoints/credentials на процесс. Для нескольких реальных заказчиков нужны отдельные настройки источника и доступа на каждого заказчика, включая привязку учётных данных при приёме и ограничение Splunk поиска. Один глобальный поисковый шаблон нельзя считать границей изоляции заказчиков. До такой доработки запускайте CONNECTED как отдельный экземпляр для одного заказчика.

## Что делают адаптеры

| Система | Чтение | Запись и ограничение |
| --- | --- | --- |
| Splunk | REST search jobs по фиксированному SPL, завершение задания, страницы результатов, опрос с checkpoint и перекрытием окна, поиск связанных событий, health | Базовый Splunk не предоставляет универсальной операции закрытия алерта. Метод `close_alert` требует отдельной реализации под ваш объект ES/SOAR. |
| TheHive | Проверка доступности, поиск кейса по устойчивому тегу перед повтором и получение допустимых статусов | План записи сохраняется в БД до запроса: кейс, страница хронологии, проверенные observable и задачи. Каждый шаг имеет свой статус и ключ идемпотентности. Изменение статуса и ограниченного набора полей кейса требует `update_case` и ручного запроса admin с readback. Проверьте формат и права на вашей версии TheHive. |
| MISP | Поиск индикатора, получение ограниченной выдачи событий, health | Отправка сведений наружу не реализована. Статусы получения, обработки L1 и передачи L2 сохраняются отдельно. Аналитик меняет статус L1, администратор вручную фиксирует передачу L2 с номером подтверждения; автоматического подтверждения нет. |

План TheHive собирается только из сохранённых алертов, доказательств и решения одного заказчика и расследования. Он включает заголовок, приоритет, теги класса и плейбука, интервал событий, обоснование, хронологию, ссылки на источник, до 20 проверенных observable, задачу принятия эскалации и до четырёх задач по недостающим данным. Исходные ссылки помечены как переданные источником и не подтверждены самим приложением; текст ограничен и маскируется по известным шаблонам секретов. Ссылки на доказательства «за/против» переносятся при наличии сохранённых claims. MITRE ATT&CK автоматически в кейс сейчас не переносится. `CaseWrite` сохраняет каждый намеренный запрос и его ключ до внешней записи, а ответ `unknown` требует readback перед повтором.

`GET /api/cases` и страница «Кейсы» читают последние 100 локальных кейсов своего заказчика, сведения из сохранённого плана и результаты подтверждённых шагов записи. Статус синхронизации `pending`, `unknown`, `failed` или `confirmed` относится к локально известным операциям и не заменяет новое чтение состояния кейса в TheHive. Для `unknown` используйте ручную сверку, а не повторяйте запись вслепую. Ссылки на исходные события с query или fragment не показываются; само приложение не подтверждает достоверность внешнего источника.

## Состояния и метрики

`pipeline_state` фиксирует проверяемые переходы от `RECEIVED` через `VALIDATED`, `ENRICHING`, `TRIAGING`, `TRIAGED` к ветвям кейса, закрытия, ручной проверки, локального подавления или ошибки. Каждый переход добавляет запись `PipelineTransition` в одной транзакции с состоянием алерта; история доступна в `GET /api/investigations/{id}`. Путь `SUPPRESSED` требует отдельной NOISE-политики и не означает закрытия инцидента в Splunk или TheHive.

`GET /api/metrics` доступен только `admin` и возвращает агрегаты из БД одного заказчика: число поступивших и дедуплицированных алертов, решения по пяти классам, успешные действия создания кейса, попытки и отказы автозакрытия, длительность завершённых расследований, ошибки интеграций и глубину очереди. `triage_results_total` считает записи решений, включая ручные и повторные, а не уникальные алерты. `auto_close_attempts_total` считает только автоматические попытки с отдельной записью аудита `auto_close_attempted`; ручные закрытия исключены. `automated_handling_rate` — доля завершённых расследований с итогом `escalated`, `suppressed` или `auto_closed`, у которых нет записанного review или ручного действия. При отсутствии завершённых расследований поле равно `null`; это не оценка точности или экономии труда. `queue_depth` считает алерты со статусом `queued` или `running`. Это JSON-снимок по запросу, не Prometheus exporter и не доказательство полноты поступления логов.

`GET /api/integrations` возвращает семь компонентов: Splunk, TheHive, MISP, Ollama, базу данных, Redis и worker. Для проверенного компонента показываются время последней проверки, последней успешной проверки, последней ошибки и безопасный тип ошибки (`0009_integration_health_history`). В DEMO Redis и отдельный worker имеют `not_applicable`; при ненастроенной модели Ollama имеет `not_configured`. Для Splunk доступность API и свежесть поступления событий оцениваются отдельно; зелёная проверка API не подтверждает полноту логов. При сбое worker после уже зафиксированного терминального действия восстановление не возвращает такой алерт в очередь.

`GET /api/audit` возвращает операцию, время, исполнителя и вычисленное поле `outcome`. Значение `recorded` означает, что событие записано в аудит, и не утверждает успешность внешнего действия. Вход `/api/auth/login` ограничивает имя 100 символами, пароль 1024 символами и число ошибочных попыток.

При потере ответа после внешнего запроса действие может иметь статус `unknown`. Оно не считается успешным; администратор запускает сверку через `/api/actions/{id}/reconcile`. Для необратимых или плохо сверяемых операций добавьте собственный адаптер со стабильным внешним ключом и подтверждённой идемпотентностью.

Параметры `CONNECTED_WRITES_ENABLED=false` и пустой `CONNECTED_ALLOWED_ACTIONS` оставляют операции записи запрещёнными. После пилотного периода в `observe` администратор может согласованно включить конкретные `create_case`, `update_case` или `suppress_noise` в `CONNECTED_ALLOWED_ACTIONS`, установить `CONNECTED_WRITES_ENABLED=true`, затем изменить уровень на `controlled_automation` или `approved_response`. Уровни `controlled_automation`, `auto_close` и `approved_response` допускают автоматическое создание кейса `TP` при разрешённом `create_case`; ручные действия admin доступны только при `controlled_automation` или `approved_response` и проходят отдельный gate. `update_case` разрешает администратору выбрать допустимый статус TheHive или запросить PATCH `/api/cases/{case_id}/fields` с полями `title`, `description`, `summary`, `severity`, `startDate`, `endDate`. Ответ подтверждается readback; неопределённый результат остаётся `unknown` до сверки через `/api/actions/{id}/reconcile`. Изменение уровня записывается в аудит. Запись не следует включать до проверки правил и внешних операций на тестовой инсталляции.

Узкий Root SSH путь выдаёт `FP` с допуском к закрытию, только когда детектор заявил успех, а отдельное связанное событие Splunk с тем же `detector_event_id` подтверждает отказ и нет совпадающего события успеха. Затем независимый серверный gate требует действующую утверждённую FP-политику с точной областью, полные доказательства, один исходный алерт в расследовании и разрешённый уровень. Групповое закрытие нескольких алертов запрещено, потому что текущий `close_alert` принимает один `source_event_id`; такие расследования требуют ручного разбора. Повторная сверка действия с результатом `unknown` привязана к исходному ID алерта и ID события; второе действие закрытия в том же расследовании запрещено. Глобальный `AUTO_CLOSE_ENABLED` по умолчанию выключен и нужен для автоматического, но не для разрешённого ручного закрытия администратором. Сценарий `root_parser_false_positive` проверяет это в DEMO с симулированным Splunk. Базовый адаптер Splunk в CONNECTED явно отклоняет `close_alert`; для реального закрытия нужен отдельный проверенный адаптер под используемый ES/SOAR.

## Утверждение FP-политики

`admin` создаёт черновик через `POST /api/exceptions` и может создать новую версию через `POST /api/exceptions/{id}/versions`. Отдельный пользователь с ролью `policy_approver` утверждает последнюю версию через `POST /api/exceptions/{id}/approve`; автор не вправе утверждать собственную запись. Администратор создаёт эту учётную запись через `POST /api/users` с `role=policy_approver`. Утверждение новой версии переводит прежнюю в `superseded`. `policy_approver` или `admin` может отозвать активную версию через `POST /api/exceptions/{id}/revoke` с обоснованием; `GET /api/exceptions/{id}/history` возвращает версии и события.

Утверждение допускается только для `root_ssh`, `vpn_country`, `ipsec_failure`, `brute_force`, `powershell`, с владельцем, содержательным обоснованием, непустым точным `scope` и интервалом не длиннее 90 дней. Нужные поля области: Root SSH — `host`, `src_ip`, `auth_method`; VPN/IPsec — `peer`, `device`, `tunnel`; brute force — `user`, `src_ip`; PowerShell — `host`, `user`, `command_line`. `entity` должно совпадать с одним из значений области; wildcard запрещён. Действие повторно проверяет область по исходному событию, время события и текущее время, статус версии, независимое утверждение, событие политики и запись аудита. Черновик, истёкшая, отозванная или заменённая версия не действуют. Сейчас только Root SSH плейбук использует этот FP-маршрут.

Согласованные работы имеют временной интервал и область `scope`; плейбуки учитывают их как контекст, а не как утверждённую FP-политику. Сценарий ошибки настройки IPsec проверяет разрешённый peer, устройство и туннель в локальной инвентаризации; разрешённый site-to-site VPN также опирается на известный peer. Эти наблюдаемые события получают `NOISE` или `BENIGN_TRUE_POSITIVE`. Для NOISE доступна отдельная политика ниже; без неё алерт остаётся на проверке. Для реального пилота нужно утвердить справочник активов и способ независимой проверки полей.

## Утверждение NOISE-политики

`admin` создаёт черновик через `POST /api/suppression-policies` и новую версию через `POST /api/suppression-policies/{id}/versions`. Другой пользователь с ролью `policy_approver` утверждает последнюю версию; `admin` или `policy_approver` может отозвать её с причиной. История версий и событий доступна через `GET /api/suppression-policies/{id}/history`. Интерфейс выполняет те же действия в разделе «Подавление шума».

Утверждение разрешено только для `ipsec_failure` с точным `scope` из четырёх полей `peer`, `device`, `tunnel`, `failure_reason`, владельцем, обоснованием и сроком до 30 дней; `entity` должен равняться `peer`. Перед применением сервер перепроверяет совпадение области и срока, запись независимого утверждения, инвентарь, согласованную работу, низкую/среднюю критичность, отсутствие кейса, конфликта и ошибки интеграции. В CONNECTED нужны успешный readback TheHive и включённый в `CONNECTED_ALLOWED_ACTIONS` `suppress_noise` при `CONNECTED_WRITES_ENABLED=true`. Результат — только локальное `SUPPRESSED`; внешние объекты не закрываются. Аналитик может вернуть алерт на проверку.

## Формат приёма и импорт

Поля нормализованного алерта для JSON/CSV импорта: `source`, обязательный `source_event_id`, `rule`, `title`, `severity`, обязательный `event_at` со смещением или в UTC, `original_timezone`, `raw` (объект), необязательные `events` (массив вложенных событий). Одинаковый `(tenant_id, source, source_event_id)` считается повторной доставкой. Пример JSON для импорта администратором:

```json
{
  "source": "pilot_fixture",
  "source_event_id": "pilot-0001",
  "rule": "generic",
  "title": "Проверка пути приёма",
  "severity": "medium",
  "event_at": "2026-10-21T08:00:00+00:00",
  "original_timezone": "UTC",
  "raw": {"host": "test-host-01", "message": "Тестовое событие"}
}
```

`POST /api/ingest/import` принимает файл JSON (один объект или массив) либо CSV; требуется токен `admin`. Максимальный размер — 2 МБ и 1000 записей. Внешний webhook использует секрет в пути URL, привязанный к заказчику; дополнительная HMAC-подпись поддерживается заголовком, но пока не обязательна. Берегите полный URL как секрет, проверьте журналы всех proxy и настройте подписанный приём до пилота. Путь ограничивает размер тела 1 МБ при чтении. Одинаковый нормализованный fingerprint в пределах TTL выявляет повтор без стабильного ID; корреляция требует совместимых сущностей, а не одного присланного ключа.

Если отдельная строка опроса Splunk не проходит нормализацию, она сохраняется в `ingestion_quarantine` с причиной, временем, числом повторов, исходным размером и SHA-256. Сохранённый фрагмент исходного JSON ограничен 256 КиБ и может содержать чувствительные данные. Список `GET /api/ingestion-quarantine` возвращает только метаданные; полный сохранённый фрагмент доступен администратору своего заказчика через `GET /api/ingestion-quarantine/{id}` или раздел «Карантин приёма». После успешной записи ошибочной строки опрос продолжается, а состояние интеграции становится `degraded`; при ошибке сохранения checkpoint не сдвигается. Примените миграцию `0007_ingestion_quarantine` до запуска worker.

Исходные события и ответы интеграций считаются недоверенными. Команды PowerShell из журнала сохраняются как доказательства и не исполняются. Если используется Ollama, проверьте набор передаваемых полей, локальность endpoint, правила маскирования и срок хранения данных. Неверная схема или непроверяемая локальность модели приводит к `needs_review`; недоступность сервера даёт детерминированный fallback без автозакрытия.

## Контрольный список пилота

- Отдельная БД CONNECTED, сильные секреты, TLS и ограниченный сетевой доступ; DEMO-учётные записи недоступны.
- Реальный Splunk сохранённый поиск выдаёт ожидаемые поля и только данные одного заказчика; окна опроса, checkpoint, повтор и поздние события проверены на рестарте.
- Подпись/секрет webhook привязаны к конкретному заказчику; повторная доставка не создаёт второй алерт или внешнее действие.
- На вашей версии TheHive проверены создание кейса, запись доказательств, поиск по ключу и восстановление после неопределённого ответа.
- На вашей версии MISP проверены права чтения, формат индикаторов и сообщений; статус обработки L1 и передачи L2 не смешивается.
- Пять плейбуков сопоставлены с фактической схемой логов, активами, согласованными работами и сроками исключений. Закрытие разрешается только по проверяемым независимым данным.
- Пробный период в `observe`: аналитик сверяет каждый вердикт с исходными логами, отмечает пропуски и ошибочные решения, измеряет задержку очереди и качество данных.
- Проверены отказ Splunk/TheHive/MISP, недоступность Redis/PostgreSQL, восстановление worker, очередь ошибок, действие `unknown` и ручная сверка.
- Проверена серверная изоляция заказчиков на API, приёме, опросе источника, экспорте отчёта и внешних действиях.
- Утверждён порядок ручной эскалации, уведомления заказчика и передачи смены; отчёт строится из фактов и не заменяет журнал подтверждений.
