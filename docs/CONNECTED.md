# Подключение к реальным системам и пилот

Режим CONNECTED предназначен для ограниченного пилота после проверки контрактов на конкретных установленных версиях Splunk, TheHive и MISP. Начинайте с чтения и ручного разбора (`observe`). Не используйте учётные данные или том PostgreSQL от DEMO для CONNECTED: при первом запуске создаются пользователи и политика заказчика, а повторное заполнение существующей БД не выполняется.

## Подготовка

1. Разверните отдельную копию проекта со своим `.env` и томами БД/Redis. Для всех команд ниже в PowerShell задайте имя Compose-проекта, отличное от DEMO, например `$env:COMPOSE_PROJECT_NAME = 'soc-pilot-01'`; при повторном открытии терминала задайте его снова. Скопируйте `.env.example` в `.env`, задайте `MODE=CONNECTED`, сильные `POSTGRES_PASSWORD`, `JWT_SECRET`, `WEBHOOK_SECRET` и `CONNECTED_ADMIN_PASSWORD`. При необходимости задайте `CONNECTED_ANALYST_PASSWORD`. Не храните реальные значения в Git. Приложение отвергает БД, в которой уже есть заказчик другого режима. Если DEMO запущен на том же компьютере, сначала освободите опубликованный порт `5173` либо используйте другой хост.
2. Ограничьте доступ к адресу сервиса, настройте TLS на внешнем reverse proxy и журналирование без секретов. В текущей конфигурации Compose наружу опубликован только порт веб-интерфейса `5173`; API доступен через его `/api/` proxy. Проверьте фактический сетевой маршрут и правила доступа до приёма событий.
3. Выдайте отдельные API credentials с минимальными правами и задайте `SPLUNK_BASE_URL`, `SPLUNK_TOKEN`, `THEHIVE_BASE_URL`, `THEHIVE_API_KEY`, `MISP_BASE_URL`, `MISP_API_KEY`. Используйте HTTPS с доверенным сертификатом. Клиенты выполняют проверку TLS и ограничивают время запросов. Для проверенного адаптера TheHive 5.7 явно задайте `THEHIVE_API_VERSION=5.7`; пустое значение или иная версия запрещает запись. Сверьте фактическую версию по `/api/v1/status` вашей установки до пилота.
4. Настройте фиксированный `SPLUNK_SEARCH_TEMPLATE` со строго разрешённым index и окном `{earliest}`/`{latest}`. Проверьте его напрямую в своей версии Splunk, включая поиск связанных событий. `SPLUNK_POLL_SECONDS` и `SPLUNK_OVERLAP_SECONDS` задают частоту и перекрытие опроса; Compose передаёт их в `backend`, `worker` и `beat`.
5. До запуска CONNECTED примените всю цепочку Alembic `0001_initial` → `0002_case_writes` → `0003_policy_approval` → `0004_classification_state`: `docker compose build backend`, затем `docker compose run --rm backend alembic upgrade head`. После этого запустите `docker compose up --build -d` и проверьте `docker compose ps`, `docker compose exec backend alembic current`, вход, `/api/health/ready`, страницу интеграций, поступление алерта, расследование и аудит. Состояние доступности API и фактическая свежесть событий проверяются отдельно.

## Локальная Ollama

Модель необязательна. Когда `OLLAMA_BASE_URL` и `OLLAMA_MODEL` пусты, решения формирует помеченный детерминированный анализатор. Чтобы включить Ollama в локальной сети Compose, сначала запустите только сервис модели и **отдельным контролируемым шагом** загрузите заранее выбранную модель:

```powershell
docker compose --profile llm up -d ollama
$approvedModel = 'имя-и-тег-утверждённой-модели'
docker compose --profile llm exec ollama ollama pull $approvedModel
```

После загрузки задайте в `.env` `OLLAMA_BASE_URL=http://ollama:11434` и `OLLAMA_MODEL` равным точному имени и тегу загруженной модели, затем запустите `docker compose --profile llm up --build -d`. Автоматической загрузки модели при старте нет. Порт Ollama не опубликован на хосте. Для полностью офлайн-развёртывания заранее перенесите проверенный локальный model store в том `ollama_data` и не разрешайте сервису выход в Интернет. Переменная `OLLAMA_NO_CLOUD=1` в Compose запрещает облачные функции сервера; приложение дополнительно проверяет `/api/tags` перед передачей событий и отклоняет модели с признаками удалённого исполнения. Сам по себе локальный адрес не доказывает, что модель локальна.

`OLLAMA_TIMEOUT_SECONDS`, `OLLAMA_MAX_INPUT_CHARS`, `OLLAMA_MAX_OUTPUT_BYTES`, `OLLAMA_NUM_CTX` и `OLLAMA_MAX_CONCURRENT` ограничивают запрос. Последний предел действует в каждом процессе worker; суммарный лимит нескольких процессов дополнительно определяется их количеством и настройками Ollama. Приложение передаёт только ограниченный набор доказательств с базовым маскированием распространённых секретов; сверьте реальные схемы логов и сетевую изоляцию до передачи чувствительных данных. Версия промпта, имя модели и краткий digest включаются в сохранённое обоснование решения. При недоступности Ollama применяется детерминированное решение без автозакрытия; невалидный или непроверяемый ответ уходит в `needs_review`. Ollama не получает инструменты и не может выполнять действия напрямую.

Текущая реализация предполагает один настроенный набор API endpoints/credentials на процесс. Для нескольких реальных заказчиков нужны отдельные настройки источника и доступа на каждого заказчика, включая привязку учётных данных при приёме и ограничение Splunk поиска. Один глобальный поисковый шаблон нельзя считать границей изоляции заказчиков. До такой доработки запускайте CONNECTED как отдельный экземпляр для одного заказчика.

## Что делают адаптеры

| Система | Чтение | Запись и ограничение |
| --- | --- | --- |
| Splunk | REST export по фиксированному SPL, опрос с checkpoint и перекрытием окна, поиск связанных событий, health | Базовый Splunk не предоставляет универсальной операции закрытия алерта. Метод `close_alert` требует отдельной реализации под ваш объект ES/SOAR. |
| TheHive | Проверка доступности, поиск кейса по устойчивому тегу перед повтором и получение допустимых статусов | План записи сохраняется в БД до запроса: кейс, страница хронологии, проверенные observable и задачи. Каждый шаг имеет свой статус и ключ идемпотентности. Изменение статуса кейса требует `update_case` и ручного запроса admin. Проверьте формат и права на вашей версии TheHive. |
| MISP | Поиск индикатора, получение ограниченной выдачи событий, health | Отправка сведений наружу не реализована. Статусы получения, обработки L1 и передачи L2 сохраняются отдельно. Аналитик меняет статус L1, администратор вручную фиксирует передачу L2 с номером подтверждения; автоматического подтверждения нет. |

План TheHive собирается только из сохранённых алертов, доказательств и решения одного заказчика и расследования. Он включает заголовок, приоритет, теги класса и плейбука, интервал событий, обоснование, хронологию, ссылки на источник, до 20 проверенных observable, задачу принятия эскалации и до четырёх задач по недостающим данным. Исходные ссылки помечены как переданные источником и не подтверждены самим приложением; текст ограничен и маскируется по известным шаблонам секретов. Ссылки на доказательства «за/против» переносятся при наличии сохранённых claims. MITRE ATT&CK автоматически в кейс сейчас не переносится. `CaseWrite` сохраняет каждый намеренный запрос и его ключ до внешней записи, а ответ `unknown` требует readback перед повтором.

## Состояния и метрики

`pipeline_state` фиксирует проверяемые переходы от `RECEIVED` через `VALIDATED`, `ENRICHING`, `TRIAGING`, `TRIAGED` к ветвям кейса, закрытия, ручной проверки или ошибки. Каждый переход добавляет запись `PipelineTransition` в одной транзакции с состоянием алерта; история доступна в `GET /api/investigations/{id}`. `SUPPRESSED` присутствует в модели, но штатный процесс пока не переводит в него алерты.

`GET /api/metrics` доступен только `admin` и возвращает агрегаты из БД одного заказчика: число поступивших и дедуплицированных алертов, решения по пяти классам, успешные действия создания кейса, попытки и отказы автозакрытия, длительность завершённых расследований, ошибки интеграций, глубину очереди и открытые ошибочные задачи. `triage_results_total` считает записи решений, включая ручные и повторные, а не уникальные алерты. `queue_depth` считает алерты со статусом `queued` или `running`. Это JSON-снимок по запросу, не Prometheus exporter и не доказательство полноты поступления логов.

При потере ответа после внешнего запроса действие может иметь статус `unknown`. Оно не считается успешным; администратор запускает сверку через `/api/actions/{id}/reconcile`. Для необратимых или плохо сверяемых операций добавьте собственный адаптер со стабильным внешним ключом и подтверждённой идемпотентностью.

Параметры `CONNECTED_WRITES_ENABLED=false` и пустой `CONNECTED_ALLOWED_ACTIONS` оставляют операции записи запрещёнными. После пилотного периода в `observe` администратор может согласованно включить конкретные `create_case` или `update_case` в `CONNECTED_ALLOWED_ACTIONS`, установить `CONNECTED_WRITES_ENABLED=true`, затем изменить уровень на `controlled_automation` или `approved_response`. Уровни `controlled_automation`, `auto_close` и `approved_response` допускают автоматическое создание кейса `TP` при разрешённом `create_case`; ручные действия admin доступны только при `controlled_automation` или `approved_response` и проходят отдельный gate. `update_case` работает при `controlled_automation` или `approved_response`: администратор выбирает значение из списка доступных статусов TheHive. Неопределённый результат сохраняется как `unknown`; сверка читает внешний статус перед подтверждением успеха. Изменение уровня записывается в аудит. Запись не следует включать до проверки правил и внешних операций на тестовой инсталляции.

Узкий Root SSH путь выдаёт `FP` с допуском к закрытию, только когда детектор заявил успех, а отдельное связанное событие Splunk с тем же `detector_event_id` подтверждает отказ и нет совпадающего события успеха. Затем независимый серверный gate требует действующую утверждённую FP-политику с точной областью, полные доказательства и разрешённый уровень. Глобальный `AUTO_CLOSE_ENABLED` по умолчанию выключен и нужен для автоматического, но не для разрешённого ручного закрытия администратором. Сценарий `root_parser_false_positive` проверяет это в DEMO с симулированным Splunk. Базовый адаптер Splunk в CONNECTED явно отклоняет `close_alert`; для реального закрытия нужен отдельный проверенный адаптер под используемый ES/SOAR.

## Утверждение FP-политики

`admin` создаёт черновик через `POST /api/exceptions` и может создать новую версию через `POST /api/exceptions/{id}/versions`. Отдельный пользователь с ролью `policy_approver` утверждает последнюю версию через `POST /api/exceptions/{id}/approve`; автор не вправе утверждать собственную запись. Администратор создаёт эту учётную запись через `POST /api/users` с `role=policy_approver`. Утверждение новой версии переводит прежнюю в `superseded`. `policy_approver` или `admin` может отозвать активную версию через `POST /api/exceptions/{id}/revoke` с обоснованием; `GET /api/exceptions/{id}/history` возвращает версии и события.

Утверждение допускается только для `root_ssh`, `vpn_country`, `ipsec_failure`, `brute_force`, `powershell`, с владельцем, содержательным обоснованием, непустым точным `scope` и интервалом не длиннее 90 дней. Нужные поля области: Root SSH — `host`, `src_ip`, `auth_method`; VPN/IPsec — `peer`, `device`, `tunnel`; brute force — `user`, `src_ip`; PowerShell — `host`, `user`, `command_line`. `entity` должно совпадать с одним из значений области; wildcard запрещён. Действие повторно проверяет область по исходному событию, время события и текущее время, статус версии, независимое утверждение, событие политики и запись аудита. Черновик, истёкшая, отозванная или заменённая версия не действуют. Сейчас только Root SSH плейбук использует этот FP-маршрут.

Согласованные работы имеют временной интервал и область `scope`; плейбуки учитывают их как контекст, а не как утверждённую FP-политику. Сценарий ошибки настройки IPsec проверяет разрешённый peer, устройство и туннель в локальной инвентаризации; разрешённый site-to-site VPN также опирается на известный peer. Эти наблюдаемые события получают `NOISE` или `BENIGN_TRUE_POSITIVE` и остаются на проверке без закрытия. Для реального пилота нужно утвердить справочник активов и способ независимой проверки полей.

## Формат приёма и импорт

Поля нормализованного алерта для JSON/CSV импорта: `source`, обязательный `source_event_id`, `rule`, `title`, `severity`, обязательный `event_at` со смещением или в UTC, `original_timezone`, `raw` (объект), необязательные `events` (массив вложенных событий). Одинаковый `(tenant_id, source, source_event_id)` считается повторной доставкой. Пример JSON для импорта администратором:

```json
{
  "source": "pilot_fixture",
  "source_event_id": "pilot-0001",
  "rule": "generic",
  "title": "Проверка пути приёма",
  "severity": "medium",
  "event_at": "2026-10-21T08:00:00+00:00",
  "original_timezone": "UTC",
  "raw": {"host": "test-host-01", "message": "Тестовое событие"}
}
```

`POST /api/ingest/import` принимает файл JSON (один объект или массив) либо CSV; требуется токен `admin`. Максимальный размер — 2 МБ и 1000 записей. Внешний webhook использует отдельный секрет; проверьте его форму и привязку к заказчику в вашем развёртывании. Не размещайте секрет в общедоступных URL, логах или истории команд. До пилота настройте подписанный приём и убедитесь, что отправитель не может выбрать чужой `tenant_id`.

Исходные события и ответы интеграций считаются недоверенными. Команды PowerShell из журнала сохраняются как доказательства и не исполняются. Если используется Ollama, проверьте набор передаваемых полей, локальность endpoint, правила маскирования и срок хранения данных. Неверная схема или непроверяемая локальность модели приводит к `needs_review`; недоступность сервера даёт детерминированный fallback без автозакрытия.

## Контрольный список пилота

- Отдельная БД CONNECTED, сильные секреты, TLS и ограниченный сетевой доступ; DEMO-учётные записи недоступны.
- Реальный Splunk сохранённый поиск выдаёт ожидаемые поля и только данные одного заказчика; окна опроса, checkpoint, повтор и поздние события проверены на рестарте.
- Подпись/секрет webhook привязаны к конкретному заказчику; повторная доставка не создаёт второй алерт или внешнее действие.
- На вашей версии TheHive проверены создание кейса, запись доказательств, поиск по ключу и восстановление после неопределённого ответа.
- На вашей версии MISP проверены права чтения, формат индикаторов и сообщений; статус обработки L1 и передачи L2 не смешивается.
- Пять плейбуков сопоставлены с фактической схемой логов, активами, согласованными работами и сроками исключений. Закрытие разрешается только по проверяемым независимым данным.
- Пробный период в `observe`: аналитик сверяет каждый вердикт с исходными логами, отмечает пропуски и ошибочные решения, измеряет задержку очереди и качество данных.
- Проверены отказ Splunk/TheHive/MISP, недоступность Redis/PostgreSQL, восстановление worker, очередь ошибок, действие `unknown` и ручная сверка.
- Проверена серверная изоляция заказчиков на API, приёме, опросе источника, экспорте отчёта и внешних действиях.
- Утверждён порядок ручной эскалации, уведомления заказчика и передачи смены; отчёт строится из фактов и не заменяет журнал подтверждений.
