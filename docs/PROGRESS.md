# Состояние прототипа — 2026-11-10

## Реализовано в текущем коде

- FastAPI, React/TypeScript, Celery, PostgreSQL/Redis для Compose DEMO и отдельный локальный DEMO на SQLite с Celery eager. `scripts/run_local_demo.py` применяет Alembic к `.qa/soc-v2.sqlite` и слушает только `127.0.0.1:8001`; интерфейс Vite запускается отдельно на `127.0.0.1:5173`. Для локального варианта WSL не требуется. Прежняя `.qa/soc.sqlite` остаётся нетронутой.
- Пять версионированных плейбуков, общий маршрут неизвестного правила, корреляция, дедупликация по заказчику и исходному ID, доказательства, аудит, журнал внешних действий и отчёт смены TXT/DOCX.
- Пять классов `TP`, `FP`, `BENIGN_TRUE_POSITIVE`, `NOISE`, `INCONCLUSIVE`; совместимый `verdict` и отдельное состояние обработки. История разрешённых переходов сохраняется в `PipelineTransition`.
- Роли `viewer`, `analyst`, `admin`, `policy_approver`. Черновики, версии, независимое утверждение, отзыв и история FP-политики; проверка области, времени, авторства и записей утверждения выполняется сервером.
- Уровень `controlled_automation` для ручных запросов действия при действующей политике. План кейса TheHive фиксирует последовательные записи в `CaseWrite` до удалённого запроса; неясный результат требует внешней сверки. `/api/metrics` отдаёт агрегаты конкретного заказчика администратору.
- 34 синтетических сценария, включая узкий `root_parser_false_positive`, и ограниченный DEMO-импорт 178 записей Wazuh JSONL с исходными метками только для сравнительного счётчика.

## Границы проверки

- Только Root SSH плейбук выдаёт `FP` с `auto_close_eligible=True` при подтверждённом отдельным связанным событием Splunk ложном детекте успеха. Для закрытия дополнительно нужны утверждённая точная FP-политика и разрешённый уровень; автоматический маршрут требует `AUTO_CLOSE_ENABLED=true`. DEMO симулирует запись. Базовый Splunk-адаптер не реализует закрытие алерта в CONNECTED.
- `BENIGN_TRUE_POSITIVE` и `NOISE` остаются на ручной проверке. `SUPPRESSED` определён в графе состояний и метриках, но штатный путь подавления не реализован.
- План кейса заполняет доказательства «за/против» только при наличии сохранённых claims; автоматическое перенесение MITRE ATT&CK в текущем вызове построителя кейса отсутствует.
- У CONNECTED один глобальный набор адресов и API credentials на процесс. Для нескольких реальных заказчиков требуется раздельная настройка источников и прав; пока нужен отдельный экземпляр на заказчика. Реальные версии Splunk, TheHive, MISP и Ollama требуют контрактной проверки.
- Локальный SQLite/Celery eager DEMO не подтверждает работу PostgreSQL, Redis, отдельного worker и доставку задач при сбоях. На этом ноутбуке в предыдущей проверке Docker Linux Engine возвращал HTTP 500, а WSL отсутствовал; пользователь выбрал не устанавливать WSL. Состояние Docker/WSL следует проверить заново перед новым заявлением о Compose runtime.

## Следующий шаг

Последняя проверка backend после добавления Root SSH FP-сценария: `145 passed, 1 warning` (Starlette/httpx deprecation), Ruff — `All checks passed`. Проверку frontend после параллельных изменений нужно закончить отдельно.

1. Выполнить `npm run typecheck` и `npm run build` в `frontend` после текущих изменений; затем проверить локальный DEMO в браузере.
2. Для нового CONNECTED экземпляра применить `alembic upgrade head` до старта приложения; держать его в `observe` до проверки данных, правил, API прав и отдельной базы.
3. Проверить внешние контракты TheHive/Splunk/MISP на тестовых инсталляциях; проверить Root SSH FP на реальных данных и реализовать отдельный адаптер закрытия, если автозакрытие требуется для пилота.
