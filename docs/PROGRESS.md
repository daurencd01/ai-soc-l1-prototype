# Состояние прототипа — 2026-11-10

## Реализовано в текущем коде

- FastAPI, React/TypeScript, Celery, PostgreSQL/Redis для Compose и отдельный локальный DEMO на SQLite с Celery eager. `scripts/run_local_demo.py` применяет Alembic к `.qa/soc-v2.sqlite` и слушает `127.0.0.1:8001`; Vite работает на `127.0.0.1:5173`. Для этого пути WSL не требуется. Compose-конфигурация проверена статически, её фактический запуск на этом компьютере ещё не подтверждён.
- Нормализация основных полей и времени, сохранение исходного JSON, дедупликация по ID источника и fingerprint с TTL, ограниченная по окну и совместимости сущностей корреляция. Пять версионированных плейбуков, общий маршрут неизвестного правила, доказательства, аудит, журнал внешних действий и отчёт смены TXT/DOCX.
- Пять классов `TP`, `FP`, `BENIGN_TRUE_POSITIVE`, `NOISE`, `INCONCLUSIVE`; совместимый `verdict` и отдельное состояние обработки. История серверных переходов сохраняется в `PipelineTransition`.
- Роли `viewer`, `analyst`, `admin`, `policy_approver`. Отдельные FP- и NOISE-политики с черновиками, версиями, независимым утверждением, отзывом и историей. Узкое локальное подавление `ipsec_failure` требует действующей точной NOISE-политики, инвентаря, согласованной работы и дополнительных серверных проверок.
- Splunk adapter создаёт ограниченные search jobs с проверкой завершения и страницами результатов. План кейса TheHive фиксирует намерения в `CaseWrite` до удалённого запроса; ручное обновление статуса и разрешённых полей проверяет readback, а неясный результат требует сверки. `GET /api/cases` возвращает локальные сведения о кейсах и статус подтверждения записей. Прямая ссылка TheHive появляется лишь при проверенном шаблоне `THEHIVE_CASE_URL_TEMPLATE` в CONNECTED и подтверждённой синхронизации.
- Локальная Ollama использует структурированный ответ с проверкой ссылок на существующие доказательства и события; `Decision` сохраняет предложение класса и уверенности, доказательства, связанные события, MITRE, имя и digest модели, версию и SHA-256 промпта (`0008_llm_provenance`). При сбое настроенной модели итог `INCONCLUSIVE` / `needs_review` блокирует автоматические действия.
- `/api/metrics` отдаёт агрегаты конкретного заказчика администратору, включая долю завершённых расследований без ручного вмешательства. Автоматические попытки FP-закрытия считаются по отдельной записи аудита, без ручных закрытий. `GET /api/integrations` показывает семь компонентов и времена последней успешной проверки и ошибки (`0009_integration_health_history`).
- Обзор, очередь алертов, отдельная страница кейсов, карточка расследования и интеграции показывают новые поля. Сверка неопределённого FP-закрытия привязана к исходному алерту; групповое закрытие нескольких исходных алертов запрещено. Восстановление worker не возвращает в очередь алерт с уже зафиксированным терминальным переходом.
- Webhook ограничен 1 МБ при потоковом чтении. В CONNECTED отклоняются короткие и демонстрационные JWT/webhook секреты, а также короткие, длинные и шаблонные стартовые пароли. Поля входа ограничены по длине, число ошибочных попыток ограничено. API access log встроенного nginx отключён, потому что webhook URL содержит секрет.
- Миграция `0007_ingestion_quarantine` сохраняет некорректные строки Splunk с ограниченным исходным JSON и метаданными; при успешном сохранении опрос продолжается в `degraded`. Администратор видит список метаданных и открывает исходную запись отдельно.
- 34 синтетических сценария и DEMO-импорт 178 записей Wazuh JSONL с исходными метками только для сравнительного счётчика.

- Полный backend прогон после изменений: `236 passed` (одно предупреждение Starlette TestClient/httpx из зависимости); Ruff для `app`, `tests`, `alembic` прошёл.
- `npm run build` в `frontend` прошёл с `tsc -b` и Vite.
- Локальный DEMO перезапущен через `scripts/run_local_demo.py`, миграции `0008`–`0009` применены, `/api/health/ready` вернул `ready`. Авторизованный API smoke подтвердил новые поля `/api/dashboard`, `/api/cases`, `/api/alerts`, `/api/audit` и семь имён `/api/integrations`; `case_reference` в DEMO равен `null`. Предыдущая проверка сценария `root_unapproved` создала `TP` и симулированный кейс TheHive с пятью подтверждёнными шагами.
- `docker compose config --quiet` проверяет конфигурацию, но не запускает PostgreSQL, Redis, worker и внешние сервисы.

## Границы проверки

- Только Root SSH плейбук выдаёт `FP` с `auto_close_eligible=True` при подтверждённом отдельным связанным событием ложном детекте успеха. Для закрытия нужны точная FP-политика, один исходный алерт в расследовании и разрешённый уровень; автоматический маршрут требует `AUTO_CLOSE_ENABLED=true`. DEMO симулирует запись, базовый Splunk не закрывает алерт в CONNECTED.
- `SUPPRESSED` не означает FP и не закрывает внешний инцидент. Подавление ограничено точным IPsec сценарием и остаётся на ручном разборе при отсутствии любого разрешающего условия. `triage_results_total` считает сохранённые решения, включая повторные и ручные, а не уникальные алерты.
- MITRE ATT&CK сохраняется в решении при валидном ответе модели, но автоматически не переносится в план кейса. Отчёт не выдумывает подтверждение уведомления заказчика или передачи смены.
- У CONNECTED один глобальный набор адресов и API credentials на процесс. Для нескольких реальных заказчиков требуется отдельный экземпляр либо дальнейшая изоляция источников и прав. Контракты фактических версий Splunk, TheHive, MISP и Ollama не проверены на их установках.
- Локальный SQLite/Celery eager DEMO не подтверждает работу PostgreSQL, Redis, отдельного worker и доставки задач при сбоях. Ранее Docker Linux Engine на этом ноутбуке возвращал HTTP 500, WSL отсутствовал; пользователь выбрал локальный DEMO без установки WSL. Это состояние инфраструктуры следует проверить заново перед заявлением о Compose runtime.
